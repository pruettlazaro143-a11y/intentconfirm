### 一、创建 Bob 原生可发现的 Skill

在项目根目录创建 `.bob/skills/intentconfirm/SKILL.md`，使用 YAML frontmatter：

- name: intentconfirm
- description: 明确说明何时启用：请求含有会明显改变成果的歧义、用户说 AI 理解错了、或用户主动要求先澄清；明确而简单的任务不额外追问。

按 Agent Skills 通用格式组织；保持核心指令不绑定 Bob 专有工具。Bob 适配说明可放在该目录的 references/ 中，需使用时再读取。只写当前真实支持的交互，不虚构点选按钮或工具。

这是在本地项目实现 Bob 版本的实际开发任务。不要声称它与其他环境已创建的同名 Skill 逐字一致；若没有那份源码，就如实说明依据本任务及现有项目实现。

### 二、实现核心澄清行为

1. 先读已有请求和相关上下文，区分：用户明确陈述、模型解释候选、用户确认、未知、失效、拒绝或排除。保留来源；用户清楚说过的事实不逐条重问。
2. 按“猜错会不会明显改变目标、核心流程、范围或验收”筛选缺口，每轮只问最关键的 1–3 个。不要固定每个人都回答受众、框架、预算等问卷。
3. 每题提供 2–4 个具体选择，简述它们对结果的影响。允许用户补充、说不确定或委托 AI 选择；推荐不等于自动选择。
4. 宿主有真实选择组件时使用；否则用编号/字母选项接受简短回复。没有点选工具就如实用文字，不构造“已点击”的假记录。
5. 根据选择继续问必要的上下文问题，已有答案不重问。不要强迫普通用户选择技术框架。
6. 修改需求时只让相关决定重新核对，保留无关限制和旧版本。例如从口语改成作文时移除录音作为当前范围，但保留“自己用、不要登录”。
7. “不知道”不是同意；“你决定”可授权范围内的可逆默认选择，但不能冒充用户原话，也不扩展成付费、公开发布等授权。
8. 信息足够完成下一步时停止追问。给出简短的目标、范围/排除、关键限制、可观察完成标准和剩余假设。只对新引入的重要解释做一次必要核对，已有授权不重复索取。
9. 用户原本要求开发时，澄清后继续使用 Bob 当前能力完成开发；仅要求需求单时才停在交接。不得把“生成了需求单”说成“项目已实现或验收”。
10. 不增设独立平台账户、模型 API、服务器或数据库作为 Skill 使用前提。无文件/脚本能力的宿主仍可按文字规则工作，但不能宣称执行了程序校验或具有强制状态门禁。

### 三、增加有价值的确定性检查

在 Skill 的 scripts/ 中实现一个无网络、无第三方依赖的本地检查工具，支持 JSON 需求记录；语言采用本机现有的 Python 或 Node。它是可选的检查辅助，不能成为普通短对话的负担。

检查至少包括：

- 已确认字段不能仅由模型输出的 confirmed=true 成立；记录需要引用实际用户响应。
- 来源引用必须存在，引用文本必须出现在对应来源中。用户来源和模型/第三方来源分开。
- 关键未知或失效项明确列为阻塞项，不静默采用推荐答案。
- 依赖引用合法、无循环；修改上游后，受影响的已接受项需要重新核对。
- 确认快照与当前草稿有一致性标识；改动后不能继续显示旧版本仍然覆盖新草稿。
- 拒绝项及明确排除条件保留。不要把“排除登录功能”误认为可以删除这项约束。
- 不修改输入记录，不访问密钥，不发送网络请求。

说明限制：程序只能检查提供给它的数据及结构，不能独立认证是谁说的话，也不能证明语义正确或需求完整；同一 AI 自己填入“用户同意”不能构成独立安全证据。不要宣传为不可绕过的权限系统。

允许复用已有纯状态代码，但不要把旧离线规则接口伪装成真实模型调用，也不要把旧的固定网站模板作为所有任务的提问引擎。
