# 产品与实施边界 v0.4

目标：降低“用户没有说完整、AI 收集不充分就执行”导致的结果偏差。雅思网站是样例；首个交接场景是把模糊想法转为可检查的开发规格。

## 主产品：宿主模型驱动的 Skill

`.bob/skills/intentconfirm/` 是本包的主要交付。由宿主模型识别信息缺口、提出选择并澄清，确认后交回同一宿主执行。无额外模型 API、账户或服务器要求。可选 Python 检查器只校验记录结构、证据存在和状态一致性，不能验证用户身份、语义正确或需求完整。

当前可移植 Skill 初稿由 Codex 制作；Bob任务02代码已审阅，Codex修订后的38项Skill测试通过；用户现已提供真实Bob澄清对话并反馈成品符合预期，见REAL_BOB_SESSION.md。完整使用流程以真实会话为准。下面描述的是保留的网页演示能力，不是 Skill 的必需架构。

## 网页演示的两种实现

规则模式：从部分中文信号提取候选，按模板和上下文动态选题。保留 Bob 实现及 Codex 审阅修订；有限覆盖明确显示。

DeepSeek 模式：服务端以当前需求状态请求模型，得到摘要、证据候选、每轮最多三个动态问题及就绪建议。前端不预设网站模板，不限制为雅思。用户点击下一轮才调用，不自动循环。已实现代码接入，尚未完成带真实密钥的验证。

模型负责提出语义理解与问题；确定性状态逻辑负责用户同意、来源格式校验、失效传播、版本快照与导出。证据逐字存在不保证候选在语义上得到证据支持，用户必须确认或否定。

## 澄清到交接

输入想法 → 检查候选 → 选择/自定义回答 → 模型再评估 → 人工核对完整需求 → 确认并导出。

未知不算同意。问题不适用必须由用户明确选择，并交给下一轮重新判断。模型不能用自己生成的 confirmed 字段代替用户确认。已有问题定义不可静默改写。每轮可以新增必要问题，而非固定问卷。

修改回答后，已声明的下游依赖失效；整个就绪建议过期，必须再次分析。依赖图本身由模型提出，可能不完整，因此仍需最终人工核对。历史确认快照不随新草稿改写。

导出保留原文、候选证据、用户回答与状态、拒绝项、调用模型和请求ID。仅 accepted 候选和 confirmed 回答作为当前执行范围。导出摘要是模型理解，不能覆盖已确认明细。需求确认不等于任务已经实现或验收。

## 失败处理

没有密钥、超时、网络错误、非法结构、原文证据缺失及已有定义冲突均显示错误；不生成虚假成功，不静默切到规则模型。允许重试或显式切换独立的规则模式草稿。在线模式仅用于本机，不作为公开多用户服务。
